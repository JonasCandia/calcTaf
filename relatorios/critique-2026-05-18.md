## Veredicto de Anti-Padrões

### Avaliação LLM

A interface **não é AI slop** no sentido estético mais óbvio. A escolha do neumorfismo é deliberada e consistente, o uso de `JetBrains Mono` para valores técnicos é acertado, e a paleta azul-marinho/dourado é defensável como identidade institucional do CBMRS (não é "marinha + dourado porque parece corporativo" — é a farda).

Dois sinais secundários a monitorar:

1. **Hierarquia tipográfica achatada**: tudo em `text-[9px]` / `text-[10px]` uppercase tracking-widest cria uma textura uniforme. Nada grita, nada sussurra. O score `text-6xl font-black` do resultado final quebra o padrão — bem. Mas os demais levels se borram.
2. **Opacidade como hierarquia**: usar `opacity-40` / `opacity-50` em labels e seções secundárias é um atalho que prejudica contraste. Hierarquia real exige diferença de *peso* ou *tamanho*, não só transparência.

## Impressão Geral

A ferramenta funciona. O fluxo principal (preencher → calcular → ver resultado) é direto. O neumorfismo é tratado com seriedade e não parece acidente. O problema real não é estética — é acessibilidade sistemática: foco de teclado removido explicitamente, tooltips inacessíveis no toque, e texto abaixo do mínimo de contraste em vários pontos. Uma calculadora usada por militares em contexto de avaliação física precisa funcionar no celular, sob pressão, e para toda a faixa etária dos 18 aos 70 anos.

## O Que Está Funcionando

**1. Divulgação progressiva do campo de Natação**
O campo aparece apenas quando o usuário marca o checkbox. Evita poluir a tela para os 90%+ que não farão o teste de natação. A animação de entrada (`AnimatePresence`) é suave e não atrapalha.

**2. Cálculo automático de idade a partir das datas**
Calcular a idade comparando data de nascimento e data de avaliação é um salto real de usabilidade. Reduz erro humano e poupa uma conta mental em momento de estresse pós-esforço físico.

**3. Design do cartão de resultado**
O score `6xl` com o badge de conceito ao lado é claro. A grade 2×4 de pontos por teste abaixo é uma boa escolha: mostra o detalhe sem dominar a hierarquia. O footer com aprovado/reprovado fecha o ciclo de forma definitiva.

## Issues Prioritários

### [P0] Focus indicators completamente removidos

**O que**: Todos os `<Input>` recebem `focus-visible:ring-0` e `focus:ring-0` explicitamente. O componente `nm-inset` não tem borda de foco alternativa. Resultado: zero indicação visual de onde o cursor de teclado está.

**Por que importa**: Qualquer usuário de teclado (incluindo usuários com deficiência motora, screen readers, ou simplesmente quem usa Tab para navegar) fica completamente perdido na interface. É uma falha de acessibilidade crítica que provavelmente viola a WCAG 2.1 AA.

**Fix**: Substituir `focus-visible:ring-0` por uma borda de foco compatível com o neumorfismo. Uma opção que mantém o estilo:
```css
.nm-inset:focus-within {
  box-shadow: var(--nm-shadow-in), 0 0 0 2px var(--primary);
}
```
E nos `<Input>`: trocar `focus-visible:ring-0` por `focus-visible:ring-0 focus-visible:outline-none` com o anel no container pai.

**Comando sugerido**: `impeccable audit`

### [P1] Tooltips de exercício inacessíveis em dispositivos touch

**O que**: O componente `InfoTooltip` usa `onMouseEnter` / `onMouseLeave`. Em telas touch, eventos de hover não disparam. O usuário em um celular nunca vê a descrição do exercício ("Pegada em pronação, braços estendidos...").

**Por que importa**: Essas instruções não são decorativas. São as regras de execução do teste. Um bombeiro que não sabe se "Barra Isométrica" conta segundos ou repetições vai inserir o valor errado. Isso é erro funcional, não só UX.

**Fix**: Adicionar `onClick` toggle ao tooltip, ou migrar para um componente `Popover` do shadcn/ui que já trata touch nativamente. Aumentar o alvo de toque do botão de `w-3 h-3` (12px) para pelo menos 44×44px com padding invisível:
```tsx
<button
  onClick={() => setShow(v => !v)}
  onMouseEnter={() => setShow(true)}
  onMouseLeave={() => setShow(false)}
  className="p-3 -m-3 opacity-40 hover:opacity-100 transition-opacity"
>
  <Info className="w-3 h-3" />
</button>
```

**Comando sugerido**: `impeccable adapt`

### [P1] Tabelas de referência inacessíveis antes do cálculo

**O que**: O único trigger para abrir o modal de tabelas é o clique no cartão de resultados. Sem resultados calculados, o cartão não existe. O usuário não pode consultar os valores mínimos para planejar o treino ou conferir sua pontuação antes de inserir.

**Por que importa**: Um militar pode querer consultar "quantas flexões eu preciso para tirar 7.0?" antes de preencher o formulário. A informação está lá, mas bloqueada por um fluxo condicional que não tem necessidade de ser condicional.

**Fix**: Adicionar um botão de acesso às tabelas independente dos resultados — por exemplo, um ícone `TableIcon` na seção de testes ou no header — que abra o mesmo `Dialog`. O modal já funciona; basta adicionar um trigger desacoplado:
```tsx
<Button variant="ghost" size="icon" onClick={() => setIsModalOpen(true)} className="nm-btn">
  <TableIcon className="w-4 h-4" />
</Button>
```

**Comando sugerido**: `impeccable clarify`

---

### [P1] Texto abaixo do mínimo de contraste WCAG

**O que**: Múltiplas ocorrências de texto com tamanho ≤10px e/ou opacidade reduzida:
- `text-[9px]` labels no breakdown de resultados (ex.: "Força", "Abdominal")
- `text-[10px]` com `opacity-50` no footer e section headers
- `technical-header` (`0.7rem` = 11.2px) com `text-muted-foreground` (`#636e72`)

A combinação de fonte pequena + cor já baixa + opacidade extra pode chegar a razões de contraste abaixo de 2:1 em alguns elementos, contra o mínimo de 4.5:1 (texto normal) ou 3:1 (texto grande).

**Por que importa**: Usuários acima de 40 anos — que estão dentro do escopo da aplicação (até 70 anos) — têm acuidade visual reduzida. Uma calculadora de aptidão física para militares de até 60+ anos precisa ser legível sem esforço.

**Fix**:
1. Substituir `text-[9px]` por `text-xs` (12px) no mínimo
2. Substituir `opacity-40` / `opacity-50` em labels por cores mais escuras sem opacidade
3. Usar OKLCH para garantir contraste calculável: `oklch(45% 0.03 250)` em vez de `#636e72` com opacidade

**Comando sugerido**: `impeccable typeset`

---

### [P2] Sem validação de entrada com feedback visível

**O que**: Inserir 0 em todos os campos e clicar "Calcular" produz `0.00 INSUFICIENTE` sem aviso. Inserir 999 flexões (impossível) gera pontuação máxima sem qualquer questionamento. A data de nascimento e a idade manual podem entrar em conflito silenciosamente se o usuário edita a idade depois de preencher a data.

**Por que importa**: Erros de digitação (trocar metros por km na corrida, por exemplo) geram resultados incorretos sem nenhum alerta. Em contexto oficial de avaliação, um resultado incorreto tem implicações sérias.

**Fix**: Validação mínima:
- Bloquear cálculo se algum campo obrigatório estiver em 0 (com mensagem inline)
- Definir faixas aceitáveis por sexo/idade e alertar se o valor parecer fora de escala (warning, não erro)
- Sincronizar idade e data de nascimento com um indicador visual quando há conflito

**Comando sugerido**: `impeccable harden`

## Observações Menores

- **Botão de reset (RotateCcw) sem label**: `aria-label="Limpar formulário"` está faltando. Em screen readers, o botão é anunciado como "button" sem contexto.
- **Tema dark muda o primary color**: No modo escuro, `--primary` passa de `#021859` (azul-marinho) para `#D90404` (vermelho). Isso altera o significado semântico da cor primária entre os temas, o que pode confundir usuários que alternam. Considerar manter o azul como base e usar vermelho como acento institucional apenas.
- **Score de resultado com `cursor-pointer` mas sem `role="button"`**: O `<Card>` que abre o modal usa `onClick` sem `role="button"` ou `tabIndex={0}`, quebrando a acessibilidade para teclado e screen reader.
- **`testDate` inicializado mas não exibido**: A data de avaliação é usada para calcular a idade mas não aparece na UI como confirmação — o usuário pode não perceber que é possível alterar a data de referência.
- **Fonte `Inter` declarada em `@theme` mas `Geist Variable` usada na prática**: O `@theme` define `--font-sans: "Inter"` mas depois é sobrescrito por `--font-sans: 'Geist Variable'`. A primeira declaração é letra morta e pode confundir quem mantém o CSS.

## Perguntas para Considerar

1. **"Um militar que falhou em apenas um teste precisa saber isso claramente — qual teste?"** O resultado atual mostra os pontos individuais mas não destaca o que puxou a nota para baixo. Uma linha vermelha em `<= 5.0` seria suficiente?

2. **"O que acontece quando o avaliador (não o avaliado) usa a calculadora?"** Pode haver dois perfis: quem calcula o próprio resultado e quem calcula o de outro. Para o segundo perfil, seria útil salvar múltiplos resultados.

3. **"A data de avaliação é obrigatória ou conveniência?"** Se é usada só para calcular a idade, por que não pedir diretamente a idade? (O campo já existe.) A dupla data+idade cria mais oportunidade de conflito do que resolve.

4. **"O neumorfismo funciona com temas de alto contraste do sistema operacional?"** Usuários com modo de alto contraste do Windows/iOS podem ter todos os box-shadows ignorados, tornando os campos `nm-inset` invisíveis.
